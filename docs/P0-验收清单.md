# P0 阶段验收清单

> 对应 `docs/PRD.md` §17.1（P0 交付物）与 §17.2（验收标准 1~3）。
> 本文档记录 **P0 收尾时的实测结果**，不是"应该怎样"的设计稿 ——
> 每条验收项都给出可复跑的入口命令与实际观测值，便于换机器、换数据库后原样重跑。

## 一、复跑方式

```powershell
# 0) 前置：本地启动 MySQL 与 Redis
pwsh -File scripts/init_db.ps1          # 建库 + 迁移 + 种子（幂等，可重复执行）
pwsh -File scripts/dev.ps1              # 依赖自检 + 迁移 + 起 API（Ctrl+C 停止）

# 1) 验收（新开一个终端；脚本不替你起服务）
pwsh -File scripts/verify_p0.ps1        # 全部断言；-SkipHttp 则只查库与审计链

# 2) 数据集与模型（可选，耗时约 20 分钟）
backend\.venv\Scripts\python.exe scripts\calibrate_dataset.py          # 分布标定（纯规划，秒级）
backend\.venv\Scripts\python.exe scripts\gen_dataset.py --reset --end 2026-09-23T12:00:00Z
backend\.venv\Scripts\python.exe scripts\train_model.py --version v1
#    把数据集库训练出的模型登记到演示库（训练库 ≠ 推理库，见 §五）
backend\.venv\Scripts\python.exe scripts\train_model.py --db-name risk_control --version v1 --register-only
#    模型质量核对（只读：全样本事件级/账号级 AUC 与分档占比）
backend\.venv\Scripts\python.exe scripts\verify_model_quality.py

# 3) 三个作弊场景（P0 的验收载体）
cd backend; .\.venv\Scripts\python.exe -m app.simulator --scenario all
```

## 四、数据集（PRD §14.1 口径）

生成入口：`scripts/gen_dataset.py --reset`（独立库 `risk_control_dataset` + Redis DB 2，
理由见 `ARCHITECTURE.md` §19.7）。建表走 alembic 迁移（`app.db.migrate`），
实测耗时约 20 分钟（5 万次事件网关调用）。

> **时间线锚点**：本次实测用 `--end 2026-09-23T12:00:00Z` 固定右端点。
> PRD §14.1 要求"结果可复现"，而右端点若取运行时刻，同一 seed 在不同日期、
> 不同时段重跑会得到不同的绝对时间（`night_activity_ratio` 按小时切分，会跟着漂移）。
> 因此**复跑时必须同时固定 seed 与 `--end`**；不指定 `--end` 时脚本会在结果里
> 显式打印提示。

| 项 | PRD §14.1 要求 | 实测 | 结论 |
| --- | --- | --- | --- |
| 事件总量 | 50,000 | 51,003（+2.0%） | ✅ 容差内（见注） |
| 时间跨度 | 14 天 | 14 天 | ✅ |
| 账号总数 | 约 800（含 60~80 作弊） | 800（作弊 70） | ✅ |
| 作弊样本占比 | 6% ~ 8% | 6.44% | ✅ |
| `login` | 35% | 33.8% | ✅（≤4pp 容差） |
| `order_create` | 20% | 19.5% | ✅ |
| `coupon_receive` | 18% | 20.1% | ✅ |
| `order_pay` | 15% | 14.7% | ✅ |
| `after_sale_apply` | 12% | 11.9% | ✅ |
| 随机种子 + 时间锚点 | 固定可复现 | `20260923` + `--end 2026-09-23T12:00:00Z` | ✅ |

> **关于总量的 +2%**：超出部分来自两处**取整** —— 正常账号的每人事件预算按
> `round(剩余配额 ÷ 正常账号数)` 分摊，而作弊画像的事件预算是固定值（不随配额缩放）。
> 生成器不断言"逐条等于 50,000"，只保证同量级与各类型占比落在容差内；
> 分布是否达标由 `scripts/calibrate_dataset.py`（纯规划、秒级）与
> `DatasetReport.problems()` 两处共同把关。

标签口径：`rc_event.is_cheat`（1 = 作弊账号事件 / 0 = 正常账号事件 / NULL = 线上事件），
迁移 `20260924_1258_ea80dfdd5cfb`；训练脚本**显式过滤 NULL**，因此数据集库与演示库可共用同一套表结构。

## 五、模型（PRD §8.3）

训练入口：`scripts/train_model.py --version v1`（连数据集库）；按时间 7:3 切分。

| 指标 | 实测 | 说明 |
| --- | --- | --- |
| 样本数 | 51,003（训练 35,702 / 验证 15,301） | 正样本占比 6.44%，验证段 4.10% |
| AUC | **0.8772** | 时间切分验证集 |
| KS | 0.6238 | — |
| precision@100 | 0.72 | 分数最高的 100 条里 72 条是作弊 |
| 对照：孤立森林 AUC | 0.7230 | 仅作对照，不参与线上决策 |
| 缺失率告警 | `account_age_days` 0.15% | 低于 50% 告警线 |
| 全样本事件级 AUC | 0.9516 | 含训练集，仅用于核对"模型确实在用特征" |
| 账号级 AUC（取账号内最高分） | 0.9602 | 风控的处置单位是账号，这个数更贴近业务 |
| 作弊事件高分率 | 87.6% ≥ 60 分、76.5% ≥ 80 分 | 均分 82.8 |
| 正常事件误报率 | 7.1% ≥ 60 分、3.9% ≥ 80 分 | 均分 12.2 |

> 复跑入口：`scripts/train_model.py` 出验证集指标（AUC/KS/precision），
> `scripts/verify_model_quality.py` 出全样本事件级/账号级 AUC 与上表两行分档占比
> （只读，不写库）。上表数值为 **2026-09-24 口径修正后重训**的实测结果。

> **"合成数据集训练，指标仅供演示"**：真实电商的黑产占比、行为分布与投诉回收率都不同，
> 本表只说明链路与口径正确，不代表线上表现（PRD §18 风险 2）。

模型生效方式（**训练库 ≠ 推理库**）：模型产物 `backend/models_artifacts/model_v1.json`
是跨库共享的文件，而 `rc_model_version` 是每库一张表。因此演示库需要单独登记：

```powershell
backend\.venv\Scripts\python.exe scripts\train_model.py --db-name risk_control --version v1 --register-only
```

`--register-only` 会校验"产物特征名与顺序 == 训练脚本 `FEATURE_NAMES`"再登记。
这一步不能省：`file_path` 写错时 `model_engine.load_active` 会**静默降级**为"模型不可用"
（决策照样返回 200，只是 `model_score` 恒为 0、贡献度空白）—— 属于"看起来在跑、其实没跑"。

## 六、三个作弊场景（PRD §14.2 / §14.3 / §19.6）

`cd backend; .\.venv\Scripts\python.exe -m app.simulator --scenario all` 实测：

| 场景 | 实测结论 |
| --- | --- |
| `coupon_farm`（42 新账号共用 5 设备 + 3 代理 IP 批量领券） | ✅ 农场账号 `Reject`（命中 `RC_ENV_001`、`RC_FREQ_001`）；混入的 2 个"环境干净"隐蔽账号放行 —— 单一弱信号不足以定级 |
| `refund_fraud`（老账号挑高额订单连续退款） | ✅ 前两笔放行、第 3 笔进人审；分数**逐笔升级**；命中 `RC_AMT_003` / `RC_AS_002` / `RC_AS_004` |
| `normal_day`（30 个正常用户的一天） | ✅ 71 次动作全部 `Pass`，无 `Reject`（误拦基线） |

模型链路已真正生效（不再是"规则单独决策"）：最近一次场景运行产生 1,421 条 `model_score > 0`
的决策、7,220 行 `rc_model_contribution`，样例贡献度（按 `|contrib|` 取 Top-N，正负号即方向）：

```
device_coupon_cnt_1h=120   contrib=+10.124  up    rank1
device_env_risk=95         contrib=+5.851   up    rank2
ip_coupon_cnt_1h=105       contrib=+5.436   up    rank3
device_account_cnt_24h=46  contrib=-5.208   down  rank4
user_coupon_cnt_1h=5       contrib=-4.991   down  rank5
```

> **怎么读这张表**：`rank` 按"贡献度绝对值"排序（哪个特征对这条事件的分数影响最大），
> 与"特征本身风险高低"无关。`down` 方向的权重（如 `device_account_cnt_24h`）是
> `class_weight="balanced"` 下学到的**反指纹**：正常账号在这类特征上的取值很低，
> 于是该特征被训练成"往下拉分"，与 `device_coupon_cnt_1h`（同一设备在刷券）相互抵消。
> 这是线性模型在共线特征上的正常行为，不代表"同设备账号越多越安全"（见 §七 共线性条目）。

| PRD §17.1 的阶段边界 | **已在 P0 提前交付** | PRD §17.1 把"全量数据集 + 训练"列为 P3，但 ARCHITECTURE §19.4 的 P0 清单把它列为未完成项。本轮按后者执行（需要先打通"数据集 → 训练 → 模型能上链路"端到端），属于提前而非跳过；待 PRD 修订时统一口径 |
| 前端 | 未开始（P1） | P0 只交付后端与脚本 |

## 八、收尾评审的修正记录（2026-09-24）

提交前做了一次双轴代码评审（规范轴 / 规格轴），发现的问题与处理如下 ——
留在这里是为了让"当时的判断"可追溯，也避免后续阶段重复踩同一类坑。

| 评审发现 | 性质 | 处理 |
| --- | --- | --- |
| 训练按**原始空间均值**填缺失、推理对缺失取 **z = 0**，两侧口径不等价 | **真问题**（会系统性偏移分数且不报错） | `train_model.py` 的填充/变换合并为 `_to_z`：缺失一律记 z = 0，与 `model_engine.predict` 逐字对齐；模型按新口径重训并重新登记 |
| 数据集右端点取 `utcnow()`，同 seed 跨时段重跑结果不同 | **真问题**（PRD §14.1 的"可复现"名存实亡） | 新增 `DatasetSpec.anchor` 与 `--end`，实测同参数两次重跑逐条一致（1277 条事件、分布完全相同） |
| `gen_dataset.py` 用 `Base.metadata.create_all` 建数据集库，绕过 alembic（缺审计触发器与 `alembic_version`） | 违反 AGENTS §6.4（迁移优先） | 新增 `app/db/migrate.py::upgrade_to_head`，脚本改调它；实测数据集库已带 `alembic_version=ea80dfdd5cfb` 与两个审计触发器 |
| 分布口径只由生成后 `problems()` 事后打印，**没有任何测试断言** | 缺口 | 新增 `backend/tests/test_dataset_plan.py`（13 项：可复现性、窗口边界、配额与占比、账号归属、画像预算） |
| 全样本 AUC / 分档占比没有可复跑入口（原为一次性诊断脚本的产物） | 缺口 | 新增 `scripts/verify_model_quality.py`（只读：事件级/账号级 AUC 与分档占比） |
| 生成器三处加权抽样循环重复；`rebuild_windows.py` 复制了网关的实体清单；`_commit()` 在批量模式下只 flush | 坏味道（静默漂移风险） | 抽出 `_weighted_pick`；`event_gateway.entities_of` 由两侧共用；改名 `_flush_or_commit` |
| 临时诊断脚本与评审产物留在仓库，`.gitignore` 未覆盖 | 仓库卫生 | 删除 12 个一次性文件（`_diag_*.py` ×5、`_calib.py`、`_review_*` ×4、`_gen_full.log`、`model_v0-validate.json`）；`.gitignore` 新增 `scripts/_*.py|md|txt` |
